## Intended Outcome

A fifth gradient subtype, `GRADIENT_CURVED`, sits alongside Linear/Radial/Angular/Diamond in the Gradient tab of the fill picker. It behaves exactly like Linear (same stops, same start/end endpoints) at rest — zero spine points is pixel-identical to a plain linear gradient — but the user can add points to the gradient's line on canvas and drag them to arc the whole "spine" into a smooth curve, instead of editing a single popup scalar. It renders correctly in the CanvasKit renderer, in SVG export, and in PDF export (which inherits from SVG per T-048's finding), and survives an OpenPotlood → `.fig` → OpenPotlood round trip without data loss, while degrading gracefully to a plain linear gradient if the `.fig` file is opened in real Figma or any other Figma-format reader.

**Revision 2 note (2026-08-22):** the user overrode Revision 1's single-scalar, popup-only "Bend" design. The product requirement is now an on-canvas, multi-point, editable spine: start with the plain (unbent) gradient line, click it to add points, drag points to arc the curve. See "Revision 2 — corrections and new findings" below for the full replacement of the affected decisions. Everything else in this packet (CanvasKit-shader-rejected-for-no-SVG-equivalent reasoning, the `.fig` closed-enum finding, the polyline/band rendering approach, the `Paint.type` handling) is unchanged and still holds.

## Request Coverage

- Add a gradient option called "curved", alongside linear, radial, angular and diamond.
- It behaves like linear, but the user can bend the gradient line into an arc, producing a curved gradient.

## Verified Starting State

### CanvasKit feasibility: two real candidates, one already used in this codebase for an unrelated effect

`App/packages/core/src/canvas/adjustments.ts` (whole file read) is the existing precedent for custom-shader work in this renderer. `renderer.ck.RuntimeEffect.MakeForBlender(sksl)` (`adjustments.ts:70`) compiles arbitrary SkSL and is cached in `renderer.adjustmentRuntimeEffects` capped at `MAX_PROGRAMS = 32` with oldest-evicted-first disposal (`:68-82`) — this is a **blender** (post-composite colour transform of what's already drawn), not a shader that can paint a gradient from scratch. The type that *can* paint from scratch is confirmed present in the bundled CanvasKit typings: `node_modules/canvaskit-wasm/types/index.d.ts:4009` — `RuntimeEffectFactory.Make(sksl, callback?): RuntimeEffect | null` (a genuine fragment shader, not a blender) and `:2934` — `RuntimeEffect.makeShader(uniforms, ...)`, which returns a `Shader` usable exactly like `Shader.MakeLinearGradient` (`r.fillPaint.setShader(shader)`). **A hand-written SkSL fragment shader that computes colour from position along an arced curve is technically reachable** — this settles the stub's core feasibility question: yes, CanvasKit can do it directly.

However, a custom `RuntimeEffect` shader has **no SVG representation**. SVG has no per-pixel custom-shader primitive; `<feDropShadow>`/gradient `<defs>` are the entire vocabulary. A shader-based curved gradient would render correctly on screen but would need a **completely different, lower-fidelity fallback for SVG/PDF export** (most realistically: rasterise the gradient to a `<image>`, discarding vector scalability). That contradicts this project's stated direction toward "production-grade PDF export" (`Plan/endgoal.md`) and would make curved gradients the only fill type in the app whose SVG/PDF output is not vector.

`App/packages/scene-graph/src/progressive-blur.ts` (whole file read) is the second candidate and the one the brief points at: it approximates a **continuous** ramp (blur radius varying smoothly along an axis) as `PROGRESSIVE_BLUR_BANDS = 6` discrete bands, each owning a slice of the axis with a soft alpha-mask handoff to its neighbours (`resolveProgressiveBlur`, `:95-123`). Crucially, **this exact technique already has one canvas implementation and one SVG implementation that stay in lockstep** — `App/packages/core/src/io/formats/svg/defs.ts:178-254` (`createProgressiveBlurLayers`) builds one `<linearGradient>`+`<mask>` pair per band, referencing the same `progressiveBlurGradient`/`progressiveBlurAxis` pure functions the canvas renderer uses. `Plan/Packets/T-037-progressive-layer-blur.md` (status: Done) is the proof this pattern ships and passes both canvas pixel tests and SVG/PDF parity tests in this codebase today.

### Revision 2 — data model

**Verified against `App/packages/scene-graph/src/types.ts:98-161` (`FillType`, `Fill`) and `App/packages/scene-graph/src/primitives.ts:18-25` (`Matrix`).** `Fill` (`:139-161`) has no array-typed geometry field today — every existing field is a scalar, a `Color`, or a `Matrix`. `GradientStop[]` (`gradientStops`) is the closest precedent for an ordered array field on `Fill`.

**Fixed Decision 2 (replacement).** Add:

```ts
export interface GradientSpinePoint {
  /** Position 0..1 along the base start→end line (same space as gradientStops[].position). */
  t: number
  /** Signed fraction of the base line's length, displaced perpendicular to it. 0 = on the line. */
  offset: number
}
```

and `gradientSpine?: GradientSpinePoint[]` to `Fill` (`types.ts`, beside `gradientTransform`). An absent or empty array means a plain straight line — the exact generalisation of the old "curveBend = 0" case, now proven as a real identity rather than asserted (see curve construction below). Points are authored in click-order but must be treated as **sorted by `t` ascending** when building the curve (Implementation Steps handle the sort); two points closer than `1e-4` in `t` collapse to the first (prevents a zero-length curve segment). The old scalar `curveBend` is not implemented; `GradientSpinePoint[]` with one element is its direct, strictly-more-general replacement.

**Correction to the perpendicular-axis reasoning.** The superseded Decision 2 claimed the perpendicular axis to bend along was "already defined" by `GradientTransform`'s `m01`/`m11` column. Re-reading the actual renderer and exporter code shows this is not true for `GRADIENT_LINEAR`: `applyGradientFill`'s `GRADIENT_LINEAR` branch (`App/packages/core/src/canvas/fills.ts:294-307`) calls `Shader.MakeLinearGradient([startX,startY],[endX,endY],...)` with **only** `m00`/`m02`/`m10`/`m12` (via `linearGradientEndpoints`, `fills.ts:250-262`) — no local matrix, so `m01`/`m11` have **zero rendering effect** for this fill type. The SVG exporter agrees: `createGradientDef`'s `GRADIENT_LINEAR` branch (`App/packages/core/src/io/formats/svg/defs.ts:60-80`) also reads only `m02`/`m00`/`m10`/`m12`. `DEFAULT_LINEAR_TRANSFORM` (`App/packages/core/src/canvas/overlays/gradient.ts:26`) is `{ m00:1, m01:0, m02:0, m10:0, m11:0, m12:0.5 }` — `m01`/`m11` default to zero, and `getGradientGeometry`'s `widthPoint` for `fill.type === 'GRADIENT_LINEAR'` (`overlays/gradient.ts:167-169`) is defined as `{ x: end.x, y: end.y }`, not from `m01`/`m11` either — nothing in this codebase reads that column for a linear gradient. Building spine-point offsets on top of an inert, usually-zero column would silently do nothing for the common case. **Fixed Decision 2b: the perpendicular axis is computed fresh from `S`/`E` each time**, not read from the transform: `perp = { x: -(E.y - S.y), y: E.x - S.x }` (a 90° rotation of the `S→E` vector, so `|perp| = |S→E|`). `offset = 1` therefore displaces a spine point by one full chord-length perpendicular to the base line — the same "signed fraction, ±1 is a full displacement" feel the old design intended, just anchored to real, always-nonzero geometry instead of a dead matrix column.

### Revision 2 — curve construction

**Fixed Decision 3 (replacement): a chain of cubic Bézier segments through every anchor (`S`, spine points sorted by `t`, `E`), built by the standard Catmull-Rom-to-Bézier conversion** — not a chain of quadratics. Reasoning: the spine points are literal through-points the curve must pass through (per the user's "add points to it and arc the spine"), not bend-offset descriptors for an independent per-segment control point. A through-point interpolating spline needs matched tangents at every interior anchor so segments meet without a visible kink; Catmull-Rom is the standard closed-form way to get that, and its cubic-Bézier form uses only `moveTo`/`cubicTo` in CanvasKit and `C` commands in SVG — no new primitive, and one shared, exactly-reproducible formula for both the canvas renderer (T-049a) and the SVG exporter (T-049b), meeting the same dual-use bar T-037 already proved (`progressive-blur.ts` consumed identically by `canvas/effects.ts` and `svg/defs.ts:178-254`).

Exact math, anchors `A_0 = S, A_1, …, A_m = E` (`A_1..A_{m-1}` from `gradientSpine`, sorted, deduped):

- Anchor position: for spine point `i` with `(t_i, offset_i)`, `A_i = lerp(S, E, t_i) + offset_i * perp` (`perp` per Decision 2b).
- For the segment between `A_i` and `A_{i+1}` (local anchor `t`-range `[T_i, T_{i+1}]`), with neighbours `P_prev = A_{i-1}` (or the mirrored phantom `2*A_i - A_{i+1}` when `i = 0`) and `P_next = A_{i+2}` (or the mirrored phantom `2*A_{i+1} - A_i` when `i = m-1`):
  - `C1 = A_i + (A_{i+1} - P_prev) / 6`
  - `C2 = A_{i+1} - (P_next - A_i) / 6`
  - Segment curve: `P(u) = (1-u)³A_i + 3(1-u)²u·C1 + 3(1-u)u²·C2 + u³A_{i+1}`, `u ∈ [0,1]`.
- To sample the whole spine at a **global** `t` (same 0..1 space as `gradientStops[].position`, unchanged from today): find the segment `i` with `T_i ≤ t ≤ T_{i+1}`, then `u = (t - T_i) / (T_{i+1} - T_i)` and evaluate that segment's cubic at `u`.

**Proof of the zero-point identity** (replaces the old "`curveBend = 0` is a mathematical identity" claim, now for the general case): with an empty `gradientSpine`, there is exactly one anchor pair `A_0 = S, A_1 = E` (`m = 1`), so the phantom points are `P_prev = 2S - E` and `P_next = 2E - S`. Substituting: `C1 = S + (E - (2S - E))/6 = S + (E-S)/3` and `C2 = E - ((2E-S) - S)/6 = E - (E-S)/3` — i.e. `C1`, `C2` sit at exactly 1/3 and 2/3 along the straight `S→E` segment. A cubic Bézier whose control points are evenly spaced (arithmetic progression) along the line between its endpoints is a **known identity for the straight line traversed at constant speed**: `P(u) = S + u(E-S)`, exactly the existing linear interpolation, for every `u`. **This makes "empty spine ⇒ pixel-identical to linear" a provable mathematical fact, for both the shape and the parametrisation (not just the shape), matching the brief's requirement exactly and making it a checkable unit-test assertion, not a claim.** (A one-point spine is *not* claimed identical to the old single-scalar quadratic formula — that formula is superseded; one spine point now produces a smooth Catmull-Rom arc through that point, which is the correct generalised behaviour, not a bit-for-bit reproduction of Revision 1's math.)
4. **Amended by Revision 2 (mechanism unchanged, source of sample points changed): `CURVED_GRADIENT_BANDS = 24`, a new constant in `App/packages/scene-graph/src/curved-gradient.ts` (new file — placement is now fixed, not an implementer choice, since T-049a creates this exact file).** Higher than blur's 6 because colour banding is far more perceptible to the human eye than blur-radius banding — blur bands hand off via a soft alpha fade so adjacent bands blend invisibly, but each colour band here is itself a small linear-gradient shader between two sampled points, so the visible artefact (if any) is a slight kink in the gradient's curvature between segments, not a hard seam, as long as consecutive bands share their boundary colour exactly (Decision 5 makes this automatic). 24 is a starting point verified only by inspection of the maths, not a rendered screenshot — see Open Decisions.
5. **Amended by Revision 2: per-band construction shares exact boundary colours and points, so adjacent bands cannot show a seam — now sampled from the spine chain, not a single Bézier.** Sample `N + 1 = 25` points `P_0..P_24` along the Revision 2 spine chain (`sampleGradientSpine`, see T-049a) at uniform global `t = k/24`. For each of those `t` values, resolve a colour via `colorAtT(stops, t)` (linear interpolation between the two `gradientStops` bracketing `t`, clamped at the ends — the stop colours themselves are first resolved through the existing `resolveFillColorInfo`, `fills.ts:274-288`, unchanged, exactly as `applyGradientFill` already does per stop today). For each band `k` (0..23): draw `Shader.MakeLinearGradient([P_k.x, P_k.y], [P_{k+1}.x, P_{k+1}.y], [colorAt(k/24), colorAt((k+1)/24)], [0, 1], TileMode.Clamp)` — a plain two-colour linear shader. Each band is clipped to the polygon slab between the perpendicular bisector at `P_k` and the perpendicular bisector at `P_{k+1}` (each bisector is a line through that point, perpendicular to the local tangent `P_{k+1} - P_{k-1}` (or the single adjacent segment at the two ends), extended `Math.max(node.width, node.height) * 4` past the point — the same "pad generously past the node bounds" idea `createProgressiveBlurLayers` already uses for its filter/mask regions, `svg/defs.ts:190-196`, made concrete as a 4-point clip quadrilateral). Because band `k`'s right edge and band `k+1`'s left edge are both anchored at the identical point `P_{k+1}` with the identical colour `colorAt((k+1)/24)`, there is no colour discontinuity at any seam — only a (generally imperceptible, at 24 bands) curvature discontinuity, which is what "polyline approximation of a curve" always trades off.
