## Outcome

Improve the local OpenPotlood MCP experience so that the available design actions are useful, understandable, reliable, and safe in the installed desktop application.

## Planning Boundary

Do not change the MCP implementation from this packet alone.

### 1. Tool coverage & naming

- **The full ~85-tool internal registry is exposed to MCP clients unfiltered, not the curated "core" subset.** `App/packages/core/src/tools/registry-core.ts` defines `CORE_TOOLS` (~22 tools) with a comment saying it's "registered by default in AI chat (~30 tools, ~3K schema tokens). Covers 90%+ of design sessions". `registry-extended.ts` adds ~60 more (`EXTENDED_TOOLS`). `registry.ts` concatenates both into `ALL_TOOLS`, and `App/packages/mcp/src/tool/registration.ts` loops `for (const def of ALL_TOOLS)` with no CORE/EXTENDED distinction — every MCP client gets the entire combined surface plus `list_documents`, `save_file`, `open_file`, `new_document`, `get_codegen_prompt`. The CORE/EXTENDED split that exists specifically to manage token budget and session focus for in-app AI chat is invisible over MCP. **Source-derived** (confirmed further by `server.test.ts`: `expect(tools.length).toBeGreaterThan(30)`).
- **Two different "create a node" mechanisms exist with no cross-reference in either description.** `render` (CORE, in `registry-core.ts`) builds nodes from a JSX tree, pre-processed server-side in `App/packages/mcp/src/jsx-preprocess.ts` before the RPC is even sent to the browser. `create_shape` (EXTENDED) builds nodes from flat params. An MCP client browsing tool names/descriptions alone has no signal for when to prefer one over the other. **Source-derived.**
- **Two safety-excluded tools are silently absent rather than described as restricted.** `registration.ts` line 48: `if ((!enableEval && def.name === 'eval') || def.name === 'stock_photo') continue`. `eval` and `stock_photo` are dropped from MCP registration entirely (confirmed by `server.test.ts`: `classifies sensitive tools and excludes unsafe T-009 tools`). This is a good safety default, but there is no MCP-visible explanation of *why* they're missing — a client that expects them (because the in-app AI chat has them) just sees "tool not found" with no context. **Source-derived.**
- **Naming convention is mixed across the tool list**, e.g. `set_fill`/`get_node` (verb_object) vs `node_resize`/`node_move`/`node_bounds`/`node_tree`/`node_ancestors` (object_verb, per the exported names `nodeResize`, `nodeMove`, etc. in `registry-extended.ts` imported from `structure`). Exact wire names weren't independently verified from a live tool listing, only from the TS export names and `defineTool({name: ...})` call sites, so the mapping between export identifier and actual `name:` string was spot-checked (e.g. `stock_photo`, `query_nodes`, `get_page_tree`, `batch_update`, `get_node`, `find_nodes` were confirmed directly) rather than exhaustively read for every one of the ~85 tools. **Source-derived for the confirmed names; the full-registry naming-consistency claim needs a live `listTools()` call to confirm exhaustively.**
- **`get_codegen_prompt`'s description is the only tool that gives explicit sequencing guidance** ("Get design-to-code generation guidelines. Call before generating frontend code.") — `registration.ts` lines 217–226. No other tool description in the files read carries an equivalent "call this before/after" hint (e.g. nothing on `create_shape`/`render` suggests calling `list_documents` first when multiple documents may be open). **Source-derived** (spot-checked descriptions; not exhaustive over all ~85).

### 2. Reliability & targeting

- **Document/page targeting is implemented correctly end-to-end and is well tested.** Every dynamically-registered tool gets an `automationTargetSchema` (`document_id`, `page_id`, both optional) merged into its Zod schema in `registration.ts`. `splitAutomationTarget` peels these off and forwards them as a top-level `target` alongside `{name, args}` in the RPC body. On the browser/editor side, `App/src/app/automation/bridge/target.ts`'s `resolveAutomationTarget` looks up the tab by `document_id` (`getTabById`) or falls back to the active tab, resolves `page_id` against that tab's graph, and **throws a specific error** (`Document "X" not found` / `Page "X" not found in document "Y"`) rather than silently defaulting to the wrong target. This is exercised by `App/tests/engine/mcp/stdio.test.ts`'s `tool target fields are sent in the app RPC envelope` test and by `server.test.ts`. **Strength, source-derived and test-verified.**
- **Untargeted calls are still ambiguous by design.** When `document_id` is omitted, `resolveAutomationTarget` falls back to `getTabForStore(activeStore)` — i.e. whichever tab/document is currently focused in the desktop app UI *at the moment the RPC arrives*. If a human is tabbing between open documents while an agent session is mid-flight (a normal thing to do in a desktop app), calls without an explicit `document_id` can silently land on a different document than the one the agent believes it's targeting. The safeguard (explicit target resolution + clear errors) exists, but there is no mechanism that makes "untargeted" calls deterministic across a session. **Source-derived; the actual race would need a live two-tab session to observe.**
- **Two different RPC timeout budgets exist for the same class of operation.** `App/packages/mcp/src/browser-rpc.ts` (HTTP/Streamable transport, used by the bundled MCP HTTP server and thus by the Codex CLI path) sets `RPC_TIMEOUT = 20_000` ms. `App/packages/mcp/src/stdio-bridge.ts` (the separate `stdio.ts` CLI entry point) sets `RPC_TIMEOUT = 30_000` ms. Both are flat, non-tool-aware: a trivial `get_node` and a heavy `export_pdf`/`analyze_overlaps` on a large document share the same ceiling, and there is no partial-result or progress signal — a timeout just produces `RPC timeout (20s)`/`(30s)`. **Source-derived.**
- **Disconnection errors are unusually well designed for an agent consumer.** Both `browser-rpc.ts` (`APP_NOT_CONNECTED_MESSAGE`) and `stdio-bridge.ts` (`DISCONNECTED_MESSAGE`) return a message that explicitly instructs the calling model to *stop*, tell the user the app isn't running, and *not* retry automatically or try to start the app itself. This is a strength — it's designed specifically to prevent automated retry storms/loops against a dead endpoint. **Source-derived.**
- **Reconnect handling drops in-flight work with a generic reason.** `browser-rpc.ts`'s `registerBrowser` closes any previous browser WebSocket and calls `rejectAllPending('Browser reconnected')` when a new browser registers (e.g. dev reload, or a second app instance token-swapping in). Any MCP call in flight at that moment fails with just `Browser reconnected` — a caller has no way to know whether its mutation applied or not. **Source-derived**, exercised functionally (not for this specific race) in `server.test.ts`'s "routes new requests to the latest registered desktop app after reconnect" test.
- **Path-scoping into `mcpRoot` is solid.** `resolveSafePath` in `App/packages/mcp/src/tool/output.ts` is defended against `../` traversal, sibling-directory tricks, and a specific "root-prefix" attack (`{root}-evil/file.fig` naming trick), all covered by `App/tests/engine/mcp/path-scoping.test.ts`. This directly backs the Exclusions' "no weakening of ... workspace-root ... safeguards" requirement — it's in good shape today. **Strength, source-derived and test-verified.**
- **`open_file`/`new_document` are conditionally registered, `save_file` always is, with different safety modes.** In `registration.ts`, `open_file` and `new_document` are only registered `if (resolvedRoot)` (i.e. only when `mcpRoot` is configured), and they require the given path to resolve inside that root. `save_file` is always registered; when `resolvedRoot` is set it validates the optional path the same way, but when it's *not* set the tool has no path validation at all (falls back to "uses the existing file path or prompts"). A client enumerating tools on a differently-configured install (e.g. `mcpRoot` unset) would see a smaller, inconsistent tool set with no explanation of why. **Source-derived.**
- **Session capacity is capped, and expiry is time-based only.** `App/packages/mcp/src/mcp-sessions.ts`: `MAX_MCP_SESSIONS = 10`, `MCP_SESSION_TTL_MS = 15 * 60_000`. When full, new sessions get `503 Too many active MCP sessions` with `Retry-After: 5`. There's no explicit session eviction/reuse beyond TTL expiry, so a client that reconnects often without cleanly deleting sessions (e.g. crash-restart loops) could exhaust the pool for up to 15 minutes. **Source-derived; needs a live long-running session to confirm real-world exhaustion.**

### 3. Feedback & discoverability

- **Oversized results degrade to a structured, actionable error rather than truncating silently.** `App/packages/mcp/src/result.ts`: `ok()` measures the JSON payload against `MAX_RESULT_BYTES = 900_000` and, if exceeded, converts to `fail()` with a message that names the offending tool, the byte sizes, and a concrete remediation hint ("Narrow the request with depth/root_id/node_types, get_node, or find_nodes."). The same pattern is reused for oversized exported images in `registration.ts`. This is a genuine strength for agent usability — it turns an opaque failure into next-step guidance. Verified by `App/tests/engine/mcp/result.test.ts`. **Strength, source-derived and test-verified.**
- **Errors carry only a message string, no machine-readable error code/class.** `fail()` returns `{content:[{type:'text', text: JSON.stringify({error: msg})}], isError:true}`. There is no `code` field distinguishing "not found" vs "timeout" vs "unauthorized" vs "path outside root" vs "app not connected" — an agent (or any tooling built on top of MCP results) can only branch by string-matching the message. **Source-derived.**
- **MCP client-visible tool metadata is limited to the generic `readOnlyHint`/`destructiveHint`/`openWorldHint` annotation triad**, correctly derived from `def.mutates` (verified in `server.test.ts`: `get_node` → `readOnlyHint: true, destructiveHint: false`; `set_fill`/`save_file` → `readOnlyHint: false, destructiveHint: true`). This is useful but coarse — there's no grouping/tagging (e.g. "vector ops", "variables", "advanced structure") visible to an MCP client the way `CORE_TOOLS`/`EXTENDED_TOOLS` group them internally. **Source-derived, partially test-verified for the annotation correctness claim.**
- **`get_codegen_prompt` is the only self-documenting "read this before doing X" tool**; no equivalent discovery aid exists for e.g. "call `list_documents` before targeting a specific `document_id`" or "call `get_page_tree`/`find_nodes` before blind `set_*` calls". This mirrors the naming finding above but is specifically a discoverability gap. **Source-derived, not exhaustively checked across every tool description.**
- **The desktop-app-side tool executor does emit structured debug/telemetry data for the in-app AI chat path** (`App/packages/core/src/tools/ai-adapter.ts`: `ToolLogEntry`/`ToolDebugLog`, before/after node snapshots, duplicate-call and no-op-mutation detection), but this instrumentation is specific to the Vercel AI SDK adapter used by in-app chat (`toolsToAI`) — it is **not** wired into the MCP server path (`registration.ts` has no equivalent before/after snapshotting or duplicate-detection). An external MCP client gets none of this feedback quality; only the in-app assistant does. **Source-derived** — this is a real asymmetry between the two consumers of the same tool registry.

### 4. Speed

All findings in this section are explicitly source-derived only; nothing here has been measured against a running instance, per the task constraint.

- **Every tool call is a single synchronous RPC round trip over one shared WebSocket** — `sendRpc` in `browser-rpc.ts`/`stdio-bridge.ts` sends one `{type:'request', id, ...}` message and awaits the matching `{type:'response', id}`. There's no batching at the transport level; the one batching mechanism that exists is the dedicated `batch_update` tool (`App/packages/core/src/tools/structure/batch.ts`), whose description explicitly frames it as a latency optimization: "Execute multiple modifications in one call ... Runs all updates with one layout recompute." Tools not covered by `batch_update`'s prop list still require one RPC per call. **Source-derived.**
- **Hard timeouts with no progress feedback**: 20s (HTTP path, `browser-rpc.ts`) / 30s (stdio path, `stdio-bridge.ts`) per call, flat regardless of tool weight, and no MCP progress-notification usage was found in any of the read files — a slow `export_pdf`/`export_image`/`analyze_overlaps`/`render` on a large document either finishes inside the window or fails outright with `RPC timeout (Ns)` and nothing recoverable. **Source-derived.**
- **Apparent request concurrency is not real parallelism.** The `pending` maps in both bridges are keyed by request UUID and can track multiple in-flight requests, so nothing stops an MCP client from firing several tool calls concurrently — but there is exactly one registered browser WebSocket per editor instance (`browserWs`/`browserRegistered` in `browser-rpc.ts`), and the editor executes each incoming `request` message inside its own single-threaded JS runtime (`handlers.ts`'s `handleRequest`, awaited per message). So concurrent calls queue up server-side rather than executing in parallel; there's no visible backpressure/queue-depth signal back to the caller if it over-fires. **Source-derived, architectural inference — needs a live multi-call benchmark to confirm actual serialization behaviour and any resulting latency.**
- **The health check is fast and doesn't block on anything heavy**: `server.test.ts`'s "returns health without waiting for package-manager detection" test asserts `/health` responds in under 1000ms even with no browser connected — a genuine strength for fast "is the app up" polling (used by `App/src/app/automation/mcp/spawn.ts`'s `pollHealth`). **Strength, source-derived and test-verified.**
- **A parallel, heavier-weight path exists for the in-app AI chat / Codex CLI consumer** (not the raw MCP client path, but relevant since it's how most users will actually feel MCP latency): `App/src/app/ai/chat/cli-transport.ts` spawns/waits on an external CLI process per turn with a `firstOutputTimeoutMs` default of 30,000ms and a 120,000ms inactivity timeout (`armInactivity`) that kills and fails the turn if the CLI goes quiet. The CLI itself (`App/desktop/src/codex.rs`, `spawn_codex_chat`) shells out to a natively-installed `codex.exe` per chat turn (`Command::new(executable)...spawn()`), reads stdout/stderr via blocking threads, and is configured (`codex_args`) to talk to the exact same `http://127.0.0.1:7600/mcp` bearer-token endpoint. So each chat turn pays: CLI process spawn + Codex's own reasoning loop + one or more 20s-bounded MCP RPCs, layered under a 120s inactivity ceiling. **Source-derived**; the packet's env-var-driven port note (`OPENPENCIL_MCP_PORT`/`OPENPENCIL_MCP_WS_PORT`) was not found verbatim in the read files — `stdio.ts`/`index.ts` use `WS_PORT`/`PORT`/`HOST` env vars instead (`process.env.PORT`, `process.env.WS_PORT`), and `codex.rs` hardcodes `http://127.0.0.1:7600/mcp` in `codex_args` rather than reading an env var — this is a **discrepancy worth flagging**: the "port overridable via `OPENPENCIL_MCP_PORT`/`OPENPENCIL_MCP_WS_PORT`" description in the task context does not match the env var names actually read by the sidecar entry points in this checkout. **Source-derived; needs confirmation this isn't a version/branch mismatch between the packet description and current source.**
- **No caching/memoization was found for read tools** (`get_page_tree`, `list_pages`, `get_node`, etc.) — every call re-walks and re-serializes the graph from scratch (see `nodeToTreeEntry` recursion in `App/packages/core/src/tools/read/nodes.ts`). For an agent doing iterative exploration of a large document this means repeated full (bounded by `MAX_RESULT_BYTES`) re-fetches rather than incremental reads. **Source-derived; no direct evidence either way of whether this matters in practice without live profiling.**

### Testing coverage note (relevant to all four areas)

MCP has real, non-trivial test coverage: `App/tests/engine/mcp/{parent-lifecycle,path-scoping,result,server,stdio,tools}.test.ts` and `App/tests/engine/tauri/mcp-spawn.test.ts` — covering tool execution correctness, HTTP/stdio transport behaviour, bearer-token/health-endpoint leakage, `mcpRoot` path scoping (including attack-shaped cases), sidecar spawn/token-ownership checks, and basic target-field plumbing. This is a genuine strength and gives later implementation packets in this area something to extend rather than build from nothing. The one targeting-related gap: no test was found that exercises the "no `document_id` given, active tab changes mid-session" ambiguity described above — that scenario is inferred from the `resolveAutomationTarget` fallback logic, not from any test asserting the exact behaviour.

## Ranked Improvements

Ranked by user impact vs. implementation cost vs. risk. **Safety-sensitive candidates are marked ⚠ SAFETY** and restate the specific Exclusion they touch — none of these are being approved for implementation by this packet; they need explicit agreement first per the Exclusions ("No implementation before the focus and acceptance criteria are agreed").

1. **Unify or tool-aware the RPC timeout.** Replace the flat, transport-inconsistent 20s (`browser-rpc.ts`)/30s (`stdio-bridge.ts`) timeout with either one consistent value or per-tool budgets (e.g. longer for `export_*`/`analyze_*`, shorter for simple reads). Impact: Medium–High (fixes false failures on legitimately heavy operations, addresses "speed" directly). Cost: Low (constant/config change, already well-isolated in two small files). Risk: Low, but ⚠ SAFETY-adjacent — this touches the "cancellation" area named in Exclusions; any change must keep clean, prompt cancellation semantics (no silently-longer hangs) and must not remove the caller's ability to abort.

2. **Add a machine-readable error code alongside the existing message string in `fail()`.** Impact: Medium (lets agents branch reliably instead of string-matching). Cost: Low (one function in `result.ts`, ripple through call sites). Risk: None — pure additive change, no safety boundary involved.

3. **Make untargeted (`document_id`-omitted) calls deterministic within a session** — e.g. require `document_id` once more than one document is open, or return the resolved target prominently enough that an agent can detect drift between calls. Impact: High (this is the core of "reliably hit the right document" — the single largest reliability/targeting gap found). Cost: Medium (touches `resolveAutomationTarget` and the calling convention). Risk: ⚠ SAFETY — this directly touches the "document-target" safeguard named in the Exclusions. Any change here must make targeting *more* explicit/deterministic, never looser; it must be designed and agreed explicitly before any implementation packet touches `target.ts`.

4. **Expose tool grouping/tagging to MCP clients** (e.g. via tool name prefixes, `title`, or a resource listing categories) mirroring the internal `CORE_TOOLS`/`EXTENDED_TOOLS`/read-modify-structure-variables-vector split. Impact: Medium–High (directly addresses discoverability and the "right tool" half of concern #3). Cost: Medium. Risk: None — purely additive metadata, no safety boundary.

5. **Default the MCP-exposed tool set to `CORE_TOOLS`, with `EXTENDED_TOOLS` behind an explicit opt-in** (mirroring the existing `enableEval` pattern already used for the `eval` tool). Impact: High (cuts schema/token overhead and naming ambiguity for the common case, reuses an existing, already-tested precedent). Cost: Medium (needs a clear opt-in mechanism and must not silently remove functionality users rely on). Risk: Low, but flag for explicit agreement since it changes default tool *availability* for MCP clients, which borders on the tool-coverage boundary this packet exists to plan, not decide unilaterally.

6. **Wire the existing `ai-adapter.ts` tool-debug-log pattern (duplicate-call detection, no-op-mutation detection, before/after snapshots) into the MCP path**, not just the in-app AI chat path. Impact: Medium (closes the feedback-quality asymmetry between the two consumers of the same tool registry). Cost: Medium–High (the pattern exists but needs a home in `registration.ts`/`browser-rpc.ts` rather than `ai-adapter.ts`). Risk: None — purely additive telemetry/feedback, no safety boundary.

7. **Add sequencing/discovery hints to more tool descriptions**, following the existing `get_codegen_prompt` precedent (e.g. steering toward `list_documents` before `document_id` targeting, or `get_page_tree`/`find_nodes` before blind mutation). Impact: Low–Medium. Cost: Low (description text only). Risk: None.

8. **Add test coverage for the target-ambiguity scenario** (multiple open documents, call without `document_id`, active tab changes between calls) to close the evidence gap noted above. Impact: Medium (turns an inferred risk into a confirmed, monitored behaviour). Cost: Low. Risk: None — test-only addition.

9. **Document the single-WebSocket serialization behaviour** (e.g. in a tool description or an MCP resource) so agents understand that concurrent tool calls queue rather than truly parallelize, and are steered toward `batch_update` for bulk edits. Impact: Low–Medium (sets correct expectations cheaply). Cost: Low. Risk: None.

10. **Investigate/resolve the `OPENPENCIL_MCP_PORT`/`OPENPENCIL_MCP_WS_PORT` vs. actual `PORT`/`WS_PORT` env var discrepancy** found between the task's architecture description and current `index.ts`/`stdio.ts`/`codex.rs` source, and confirm whether `codex.rs`'s hardcoded `http://127.0.0.1:7600/mcp` should instead be configurable. Impact: Low on its own, but High as a prerequisite — later packets should not build on the wrong env var names. Cost: Low (investigation), unknown until resolved for any actual fix. Risk: None to investigate; ⚠ SAFETY note only if a fix ever makes the MCP port configurable in a way that weakens the loopback-only (`127.0.0.1`) binding named in the Exclusions — any such change must keep the server loopback-only.

11. **Provide progress/partial-result feedback for long-running tools** (exports, overlap/typography analysis on large documents) instead of an all-or-nothing timeout. Impact: Medium. Cost: High (needs new transport-level support, likely MCP progress notifications end-to-end). Risk: ⚠ SAFETY-adjacent — like item 1, this touches the "cancellation" safeguard in the Exclusions; must preserve (or improve) the caller's ability to cancel cleanly, not just extend how long a call can run unattended.

12. **Investigate session-pool exhaustion behaviour** under reconnect-heavy or crash-loop conditions against the `MAX_MCP_SESSIONS = 10` / 15-minute TTL limits, and consider faster eviction of dead sessions. Impact: Low–Medium (edge case, but currently produces an opaque 503 with no remediation guidance). Cost: Low–Medium. Risk: None to investigate; any fix should tighten cleanup, not raise the cap in a way that changes resource/safety posture without explicit agreement.
