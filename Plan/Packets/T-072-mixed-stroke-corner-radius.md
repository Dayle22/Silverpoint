# T-072 — Rounded corners with mixed stroke widths

## Intended Outcome

A rectangle with uneven individual border widths remains geometrically correct when its corner radius is raised: no broken joins, square fallback corners, clipping artefacts or malformed edge intersections.

## Verified Starting State

It never reads `node.cornerRadius`/`independentCorners`/per-corner radius fields at all, so raised radius has zero effect on this path — the two perpendicular full-length lines simply overlap at a square corner, ignoring whatever rounding the fill/other stroke routes show.

## Scope and Acceptance Criteria

1. **New corner-aware path builder, `shapes.ts`.** Add `buildIndividualStrokeRingPath(r, node, align, cornerRadii): Path`, where `cornerRadii = { topLeft, topRight, bottomRight, bottomLeft }` (all four passed explicitly by the caller — do not have this function read `node.cornerRadius` itself, so the `renderSection`/`SECTION_CORNER_RADIUS` override composes cleanly). For each side compute:
   - `outerOffset(weight)` = `align === 'OUTSIDE' ? weight : align === 'CENTER' ? weight / 2 : 0`
   - `innerOffset(weight)` = `align === 'INSIDE' ? weight : align === 'CENTER' ? weight / 2 : 0`
   Build two sub-paths, wound in opposite directions, then combine with `path.op(inner, r.ck.PathOp.Difference)` (same `Path.op` pattern already used for `OUTSIDE` clipping at `strokes.ts:291` and `strokes.ts:337`) to produce one ring path — do not hand-wind a single path and rely on even-odd fill; `Difference` is the existing codebase idiom here and avoids winding-order bugs:
     - **Outer path**: walk the four outer offset lines (`top` at `y = -outerOffset(borderTopWeight)`, etc.), joined at each corner by `path.arcToRotated(rx, ry, 0, false, false, x, y)` where, for the corner between horizontal side H and vertical side V, `rx = Math.max(0, cornerRadii[corner] + outerOffset(V's weight))` and `ry = Math.max(0, cornerRadii[corner] + outerOffset(H's weight))` — i.e. the ellipse's radius on each axis grows by that axis's own adjacent side's outward offset, generalising `strokeInset()`'s `radius - inset` rule to two independent offsets per corner instead of one shared one.
     - **Inner path** (opposite winding order): same shape, `rx = Math.max(0, cornerRadii[corner] - innerOffset(V's weight))`, `ry = Math.max(0, cornerRadii[corner] - innerOffset(H's weight))`.
   - Clamp each corner's radius before the offset math so adjacent corners never overlap along a shared side — width/height budget clamp, same shape as the per-corner budget loop in `smoothCornerRadii` (`shapes.ts:115-129`) but without the smoothing-curve terms (this is a plain circular/elliptical clamp, not a superellipse). Extract just the budget-splitting loop into a small shared helper (e.g. `clampCornerRadiiToBounds(radii, width, height): CornerRadii`) used by both `smoothCornerRadii` and the new builder, rather than duplicating the loop — check whether `smoothCornerRadii`'s loop can be cleanly split before deciding between "extract" and "reimplement"; do not skip the clamp either way.
   - Zero-radius rectangle (`cornerRadii` all `0`): the outer/inner arcs collapse to plain rect corners — verify `arcToRotated` with `rx = ry = 0` degenerates to a corner point (equivalent to a `lineTo`) rather than emitting a degenerate arc command; if CanvasKit does not handle that cleanly, special-case zero radius per corner to `lineTo` instead of `arcToRotated`, matching how `drawTopRightSmoothCorner` etc. already special-case `corner.radius === 0` with a plain `lineTo` (`shapes.ts:178`, `:215`, `:252`, `:284`).
2. **Rewire `drawIndividualSideStrokes` (`strokes.ts:350`).** Change its signature to accept the same explicit `cornerRadii` shape as the new builder. When all four corner radii are `0`, keep the exact current four-`drawLine` implementation unchanged (byte-for-byte) — this preserves the zero-radius baseline test coverage and sidesteps any risk of regressing the common uniform-square-corner case. When any corner radius is `> 0`, build the ring path via `buildIndividualStrokeRingPath`, set `r.fillPaint`'s color to the already-resolved stroke color/opacity for this draw call (mirroring how `drawVectorStrokeGeometry` at `scene.ts:524` fills a stroke-outline path through `r.fillPaint` rather than stroking it — the ring is filled geometry, not a stroked line, so `r.strokePaint`'s width/cap/join settings are irrelevant to it and must not be touched), `canvas.drawPath(ringPath, r.fillPaint)`, then `ringPath.delete()`. Restore whatever `r.fillPaint` held before (color/shader) after drawing, since fills for this node may render afterward or before depending on draw order at the call site — check ordering at both call sites before assuming fills are already fully drawn.
3. **Radius source at each call site.**
   - `scene.ts:646` (`drawRegularStroke`): pass `node.independentCorners ? { topLeft: node.topLeftRadius, topRight: node.topRightRadius, bottomRight: node.bottomRightRadius, bottomLeft: node.bottomLeftRadius } : { topLeft: node.cornerRadius, topRight: node.cornerRadius, bottomRight: node.cornerRadius, bottomLeft: node.cornerRadius }` — same fan-out `makeRRect()` already does (`shapes.ts:412-434`); consider extracting a `nodeCornerRadii(node): CornerRadii` helper shared by both to avoid a third copy of this ternary.
   - `scene.ts:428` (`renderSection`): pass `{ topLeft: SECTION_CORNER_RADIUS, topRight: SECTION_CORNER_RADIUS, bottomRight: SECTION_CORNER_RADIUS, bottomLeft: SECTION_CORNER_RADIUS }` if step-1's investigation confirms sections can actually reach `independentStrokeWeights`; otherwise leave this call site's straight-line behaviour as-is and record why in the packet's status line at completion.
4. Preserve the intended per-side weights and `INSIDE` / `CENTER` / `OUTSIDE` alignment; no normalisation to one shared stroke weight, and no change to `strokeInset()` or the uniform-weight `drawRRectStrokeWithAlign()` route.
5. Do not change the radius control (`radius.ts`), selection outline, stroke-gradient model, export semantics, or add a visual workaround in the panel.
